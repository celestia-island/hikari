# ドックの配置：pin と ride

ドックはある領域に属するクロームだ——ボード下のバー、隅のページャー。スクロール領域では
ドックは `HkScrollContainer` のスロット（`dockBottom` / `dockTop`）からマウントされ、
コンテナは下部ドックの配置方法を二つ用意している（`dockMode`）。

## `pin` — 既定

ドックはスクロールビューポートの**スクロールしない** flex 兄弟になる。コンテナの下端に
固定され、決してスクロールせず、ビューポートはその高さだけ縮む。

領域の枠を所有するクロームに向く——ログ上のプログレスバー、パネル自身の端に揃うツールバー。

コンテンツ末端とドックの間の余白はウィンドウの余り次第で、コンテンツが一画面に満たない
ときは、その余り高さが両者の間に死んだ帯として残る。

## `ride`

ドックはビューポートの内容フローに入り、コンテンツの後ろ、**コンテナが実測したドック占有高**
ぶんのスペーサーの後ろに置かれ、`position: sticky; bottom: 0` で可視の下端に貼り付く：

- コンテンツが短い——ドックはコンテンツ末端に追従して自分のフロー位置に留まり、その上の余白は
  実測した占有高そのもの、ウィンドウの余り高さはドックの**下**に落ちる；
- コンテンツが長い——ドックは可視の下端に留まり（垂直軸では決して流れ去らず、二軸ボードでは
  インライン開始端に留まって横方向にも流れ去らない）、スクロール末端でも同じ余白が開く。

「ドック占有高」はコンテナが実測し `--hk-scroll-dock-bottom` として公開するボックスの高さで、
ドック自身の場所を占めるボックスであって**可視のドック面とは限らない**：ホストがこの帯の内側に
置く空間（ドックのインセット、行自身の末尾パディング）は上乗せされるので、可視のドックとの差は
ホスト自身のパディング分になる。ホストはこの公開値を読めばよく、スペーサーのレシピやマジック
ナンバーを手書きする必要はない。余白はドックの再レイアウト（行の変化、ブレークポイントの
切り替え）にも追従する。

ride ホストはさらに、コンテンツが**ビューポート下端より上で終われる**ようにしなければならない：
内容ボックスをビューポート高まで膨らませる規則（`min-height: 100%`）があると、フロー内の
スペーサーとドックが折り返し線の下に落ち、ドックは端に貼り付くしかなく、余白はウィンドウの
余りに戻ってしまう。`HkKanban` は ride ボードで自身の lanes ボックスを解放する。独自ホストも
同様にする。

同じ理由で、`autoFollow` と ride ドックの併用はサポートしない：内容ボックスを画面高で下端合わせにする
ため、ride の末尾が折り返し線の下に落ちる。両方を有効にした開発ビルドでは、コンテナのインスタンス
ごとに一度だけ警告する。

ピン留めしている間、ride のラッパーとスペーサーは `pointer-events: none` だ。イベントを受け取る必要が
あるスロット内容の部分（ドック自身の操作系）は、その部分自身で `pointer-events: auto` を宣言する
必要がある。

## ride はフレーム単位の予約ではない

ride は、内容フローの外からスクロール領域に浮かぶドックのためにビューポート上で `::after`
により `ドック高さ + 呼吸` を予約していた、あの廃止済みのレシピでは**ない**し、「ドック二つ分の
空白を予約する」ものでも**ない**。あの帯はスクロール末端より前に死んだ余白として現れ、ドックが
コンテンツに追従することもなかった。ride のドック本体はフロー内の子ノードであり、どこか別で
描かれるもののために空間を前もって確保しない。sticky こそが、余白をウィンドウではなく
コンテンツに追従させる仕組みだ。

## 選び方

| ホスト | 配置 |
|---|---|
| スクロール領域で、クロームがコンテンツに属する | `dockMode="ride"` |
| スクロール領域で、クロームが領域の枠を所有する | `dockMode="pin"` |
| キャンバス / ページのオーバーレイで、スクロール領域が所有しない | `HkDockBar` |

`ride` は垂直方向の末尾にのみ存在する。`axis="horizontal"` のコンテナは `pin` のまま
だ——そちらの末尾は交差軸だからである。
