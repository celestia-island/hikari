# ページクローム：アクションバーの文法

管理画面とコンソール画面は、1 つのヘッダー契約を共有します。ページは「用途を宣言する
スロット」を通じて右上のアクションクラスタを所有し、ページの主要な入口はページ本文では
なくクラスタ内に住みます。

## 正規スロット

登録は必ず用途を宣言します。クラスタは正規スロットを固定順位で描画し、ビューが登録した
順序には従いません：

```text
[新規作成][フィルタ][検索][更新][ウィンドウ]
```

正規スロットに該当しない用途の登録はカスタム扱いです。正規ゾーンの後ろに、登録の逆順で
右から左へ詰められます。正規ゾーンが動くことはありません。

## 新規作成ルール

ページの主たる作成アクション——新しいトップレベル実体（プロバイダー、チャネル、グループ、
アクセスルール、共有テーマライン上のテーマ）を作る入口——は、**右上クラスタ内のプラス
アイコンボタン、更新の左**です。ページ本文内の独立ボタンであってはいけません。

本文ボタンが表示していたはずのラベルは、そのボタンのアクセシブル名とツールチップに
なります。作成用ダイアログの所有権はページ側に残ります。

**文脈内の追加は免除されます。** エディタ・ダイアログ・ウィザード・カード内のサブリストに
行を追加するプラス（「モデル行を追加」「メンバーを追加」「マウント方式を追加」）は、その
局所文法の一部であり、ページの作成アクションではありません。その場に留まります。

## ジオメトリ

クラスタは 1 列の chrome です。すべてのアイコンボタンは同じサイズラダー
（`useChromeActionSize`）を歩み、グリフは 16px です。固定サイズのボタンがラダーサイズの
隣に混ざると、別ファミリーのボタンに見えます。クラスタは共有ヘルパーで組み立て、手打ちの
サイズは禁じます。

## リファレンス実装

chrome は hikari が提供します：`HkAdminHeader` のアクション行、`HkIconButton`、
`useChromeActionSize`。ホストは上記スロットを描画する `provideActionBar` /
`useActionBar` コンポーザブル経由で登録します。これがこの文法の
リファレンス実装です。

## モバイル折りたたみ

ヘッダー中央スロットやフッター中央スロットに固定されたボタン群は、電話幅の
ビューポート（<768、`useBreakpoint().isMobile`——sheet ファミリーの閾値）で
折りたたまれる：ストリップは**現在の項目**を読み上げるセレクト式トリガーになり、
選択肢はボトムシートとして開く（`HkSelectPanel` の `sheetOnMobile`）。
両形態は同一の value 契約を共有し、`?tab=` ディープリンクはブレークポイントを
跨いでも生き残る。`HkAdaptiveTabs` が既定の実装。専用行を持つ動的
プロジェクトリスト切替器（プラットフォームスイッチャー）は免除される特例であり、
模範ではない。

## ピッカーシートとピン留めされた検索欄

ドロップダウン面（`HkSelectPanel`——`HkSelect` / `HkMenu` / 各チップピッカーの
下にある一面）には 2 つの内容バンドがあり、何がどちらに属するかは交渉の
余地がありません。

- **`default` はスクロールする。** 行・カード・カタログ——面の高さを超え得る
  すべてのもの。
- **`pinnedHeader` はスクロールしない。** リストがスクロールしている間も
  手が届いていなければならない chrome。まずはライブフィルターの検索欄。
  どちらのフォームファクターでもスクロール領域の外に描画されます——
  スマートフォンではシートのタイトル行の下のバンド、デスクトップでは
  popout カラムの先頭（このとき単一のスクロールバーは body が持つ）。
  検索欄がスクロールする内容の中にあって最初のスワイプで流れてしまうのは、
  スタイルの選択ではなく欠陥です（2026-11-27）。

ピッカー/メニュー・ファミリーのスマートフォンシートは内容に沿い、**ビューポートの
80%** まで。それより長い内容は内部でスクロールします。デスクトップ popout 用に
調整した上限（`maxHeight`、例 `min(18rem, 45dvh)`）がシートに届くことは
決してありません。シートはスクロール連鎖も断ち切ります。グラバー・タイトル行・
ピン留めバンドでのスワイプは、背後のページを引きずりません。

## リストのモーション

リスト項目が変化する——追加・削除・並べ替え——とき、移動は必ず hikari の
`HkListTransition`（キー付き `TransitionGroup`、FLIP をランタイムのアニメーション
バスに報告）を通り、手書きのトゥイーンは使いません。リスト形の面（行・カード・
ウォーターフォール）すべてに 1 つの既定値：移動トラックは 0.3s、enter と leave
はそれぞれ 0.15s で移動と同時に始まります。ホストは `duration` /
`enterDuration` / `leaveDuration` の各 prop（CSS 時間。`duration` 単独なら
半分の 2 つを導出）でカスタマイズします。`surface` だけが例外です（ウィンドウ
である行はウィンドウファミリーの入退出タイミングを保ちます）。

複数選択ピッカー（`HkAffixPicker` の `multi` モード、`layout="rows"`）は、
選択のために検索欄の前に何も組み立てません。チェックされた行は先頭のチェック
マークをまとい、カタログ順でリストの先頭へ浮かび、1 本の区切り線で残りと
隔てられます。タップでトグルし、行は自分の位置へ滑らかに移動したり戻ったり
します。`layout="tags"` は値エディターの形（各項目に入力済みの値を表示）で、
検索欄の上のタグリストを保ちます。

## フッター角テキスト

ヘッダー/フッターの六つの角（左/中央/右 ×2）にテキストを置く場合は、必ず
hikari の `HkCornerText` を使う。1 インスタンス = 1 角の 1 テキストレーン。

- `align` が角を決める：`start`（左角）/`center`（中央レーン）/`end`（右角）。
  折り返した行も同じ端に寄る——右角のテキストは折行後も右寄せ。
- エントリは `nowrap` 原子：レーンはエントリの**間**でのみ折り返し、エントリ内
  では決して折らない（備案番号が番号の途中で切れてはならない）。
- 既定は chrome の弱いインク（`text-2xs` + 0.6 不透明度）。`muted: false` で
  全インクに戻る。
- 1 角に複数行（識別行 + 備案行）が必要ならインスタンスを縦に積む——固定 3rem
  のステータス帯には text-2xs 2 行が入る。
- `items` の要素形状は `{ key, text, href? }`：`key` はリスト描画が使う安定した
  識別子、`text` は表示文字列（備案番号、システム名……）、`href` は省略可能 —
  省略すると `<span>`、与えるとリンクとして描画される。
- `href` を持つ要素は常に新しいタブで開く：`target="_blank"` と
  `rel="noopener noreferrer"`（備案番号と同じ契約 — 外部サイトがログイン
  ページのウィンドウのハンドルを握ってはならない）。これはコンポーネント
  自身の挙動であり、ホストが要素を自前の `<a>` で包んではならない。
- リンクエントリ（備案リンク）は `items` + `as="nav"` + `ariaLabel`。自由内容
  （ステータスチップ）は既定スロットで `items` の後に続く。

ホストが `flex-wrap: nowrap` の一行圧縮レーンを手書きすること、固定高帯の外に
テキストを描くことを禁じる。リファレンス実装：`HkCornerText`。
