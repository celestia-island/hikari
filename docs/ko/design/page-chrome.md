# 페이지 크롬: 액션 바 문법

관리자 및 콘솔 페이지는 하나의 헤더 계약을 공유합니다. 페이지는 용도를 선언하는 슬롯을 통해
오른쪽 위 액션 클러스터를 소유하며, 페이지의 주요 진입점은 페이지 본문이 아니라 클러스터
안에 삽니다.

## 정규 슬롯

모든 등록은 용도를 선언합니다. 클러스터는 뷰가 등록한 순서와 무관하게 정규 슬롯을 고정
순위로 렌더링합니다:

```text
[생성][필터][검색][새로 고침][창]
```

정규 슬롯에 해당하지 않는 용도의 등록은 커스텀입니다. 정규 구역 뒤에 등록의 역순으로
오른쪽에서 왼쪽으로 채워지며, 정규 구역은 절대 밀리지 않습니다.

## 생성 규칙

페이지의 주 생성 액션——새로운 최상위 개체(공급자, 채널, 그룹, 접근 규칙, 공유 테마 라인의
테마)를 만드는 진입점——은 **오른쪽 위 클러스터의 플러스 아이콘 버튼, 새로 고침의 왼쪽**입니다.
페이지 본문 안의 독립 버튼이어서는 안 됩니다.

본문 버튼에 인쇄되었을 라벨은 그 버튼의 접근 가능한 이름과 툴팁이 됩니다. 생성 대화상자의
소유권은 페이지에 남습니다.

**문맥 안의 추가는 면제됩니다.** 편집기·대화상자·마법사·카드 안의 하위 목록에 행을 추가하는
플러스("모델 행 추가", "구성원 추가", "마운트 방식 추가")는 그 지역 문법의 일부이지 페이지의
생성 액션이 아니므로 제자리에 남습니다.

## 지오메트리

클러스터는 한 줄의 크롬입니다. 모든 아이콘 버튼은 같은 크기 사다리(`useChromeActionSize`)를
걷고 글리프는 16px입니다. 고정 크기 버튼이 사다리 크기의 이웃 사이에 끼면 다른 패밀리의
버튼으로 읽힙니다. 클러스터는 공유 헬퍼로 조립하고 손으로 박은 크기는 금지입니다.

## 참조 구현

크롬은 hikari가 제공합니다: `HkAdminHeader`의 액션 행, `HkIconButton`,
`useChromeActionSize`. 호스트는 위 슬롯을 렌더링하는 `provideActionBar` /
`useActionBar` 컴포저블로 등록합니다. 이것이 이 문법의 참조 구현입니다.

## 모바일 접힘

헤더 중앙 슬롯이나 푸터 중앙 슬롯에 고정된 버튼群은 전화폭 뷰포트(<768,
`useBreakpoint().isMobile` — sheet 패밀리의 임계값)에서 접힌다: 스트립은
**현재 항목**을 읽어 주는 셀렉트식 트리거가 되고, 옵션은 바텀 시트로 열린다
(`HkSelectPanel`의 `sheetOnMobile`). 두 형태는 같은 value 계약을 공유하므로
`?tab=` 딥링크는 중단점을 넘어도 유지된다. `HkAdaptiveTabs`가 기본 구현이며,
고유 행을 지닌 동적 프로젝트 목록 전환기(플랫폼 스위처)는 면제되는 특례지
따라 배울 패턴이 아니다.

## 피커 시트와 고정된 검색란

드롭다운 면(`HkSelectPanel`——`HkSelect` / `HkMenu` / 각 칩 피커 아래의 면)에는
두 개의 콘텐츠 밴드가 있으며, 무엇이 어느 밴드에 속하는지는 협상의 여지가
없습니다.

- **`default`는 스크롤됩니다.** 행, 카드, 카탈로그——면의 높이를 넘을 수 있는
  모든 것.
- **`pinnedHeader`는 스크롤되지 않습니다.** 목록이 스크롤되는 동안에도 닿아
  있어야 하는 chrome. 첫째가 실시간 필터 검색란입니다. 두 폼 팩터 모두에서
  스크롤 영역 밖에 렌더링됩니다——휴대전화에서는 시트 제목 행 아래의 밴드,
  데스크톱에서는 popout 컬럼의 머리(이때 유일한 스크롤바는 body가 담당).
  검색란이 스크롤되는 콘텐츠 안에 있어 첫 스와이프에 함께 밀려나가는 것은
  스타일 선택이 아니라 결함입니다(2026-11-27).

피커/메뉴 패밀리의 휴대전화 시트는 콘텐츠에 맞춰 **뷰포트의 80%**까지
높아지고, 더 긴 콘텐츠는 내부에서 스크롤됩니다. 데스크톱 popout용으로 조정한
상한(`maxHeight`, 예 `min(18rem, 45dvh)`)은 시트에 결 닿지 않습니다. 시트는
스크롤 연쇄도 끊습니다. 그랩버·제목 행·고정 밴드 위의 스와이프는 뒤의
페이지를 끌지 않습니다.

## 목록 모션

목록 항목이 변할 때——추가·제거·재정렬——이동은 반드시 hikari의
`HkListTransition`(키 있는 `TransitionGroup`, FLIP을 런타임 애니메이션 버스에
보고)을 통하고, 손으로 짠 트윈은 쓰지 않습니다. 목록형 면(행·카드·워터폴)
모두에 하나의 기본값: 이동 트랙은 0.3s, enter와 leave는 각 0.15s이며 이동과
동시에 시작합니다. 호스트는 `duration` / `enterDuration` / `leaveDuration`
prop(CSS 시간; `duration`만 주면 절반 두 개를 유도)으로 맞춤화합니다.
`surface`만이 예외입니다(창인 행은 창 패밀리의 입출 타이밍을 유지).

다중 선택 피커(`HkAffixPicker`의 `multi` 모드, `layout="rows"`)는 선택
때문에 검색란 앞에 아무것도 세우지 않습니다. 체크된 행은 앞쪽 체크 표시를
달고 카탈로그 순서로 목록 앞쪽에 떠오르며, 구분선 하나로 나머지와
격리됩니다. 탭하면 토글되고 행은 제 자리로 미끄러져 가거나 돌아옵니다.
`layout="tags"`는 값 편집기 형태(항목마다 입력된 값 표시)로 검색란 위의
태그 목록을 유지합니다.

## 푸터 코너 텍스트

헤더/푸터의 여섯 코너(왼쪽/가운데/오른쪽 ×2)에 텍스트를 표시할 때는 hikari의
`HkCornerText`를 쓴다. 인스턴스 하나 = 코너 하나의 텍스트 레인 하나.

- `align`이 코너를 정한다: `start`(왼쪽 코너) / `center`(가운데 레인) /
  `end`(오른쪽 코너). 줄바꿈된 행도 같은 가장자리에 붙는다 — 오른쪽 코너의
  텍스트는 줄바꿈 후에도 오른쪽 정렬.
- 항목은 `nowrap` 원자: 레인은 항목 **사이**에서만 줄바꿈하고 항목 내부에서는
  절대 줄바꿈하지 않는다(신고 번호가 번호 중간에서 끊기면 안 된다).
- 기본값은 크롬 약잉크(`text-2xs` + 0.6 불투명도). `muted: false`로 완전 잉크
  복원.
- 한 코너에 여러 행(식별 행 + 신고 행)이 필요하면 인스턴스를 세로로 쌓는다 —
  고정 3rem 상태 띠에는 text-2xs 두 줄이 들어간다.
- `items` 항목의 모양은 `{ key, text, href? }`다. `key`는 목록 렌더러가 쓰는
  안정된 식별자, `text`는 표시 문자열(신고 번호, 시스템 이름…), `href`는
  선택 사항 — 빼면 `<span>`, 주면 링크로 그려진다.
- `href`가 있는 항목은 항상 새 탭에서 열린다: `target="_blank"`와
  `rel="noopener noreferrer"`(신고 번호와 같은 계약 — 외부 사이트가 로그인
  페이지 창의 핸들을 쥐어서는 안 된다). 이것은 컴포넌트 자체의 동작이며,
  호스트가 항목을 자기 `<a>`로 감싸서는 안 된다.
- 링크 항목(신고 링크)은 `items` + `as="nav"` + `ariaLabel`. 자유 콘텐츠(상태
  칩)는 기본 슬롯으로 `items` 뒤에 온다.

호스트가 `flex-wrap: nowrap` 한 줄 압축 레인을 손으로 쓰거나 텍스트를 고정 높이
띠 밖에 그리는 것을 금지한다. 참조 구현: `HkCornerText`.
