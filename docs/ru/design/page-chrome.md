# Каркас страницы: грамматика панели действий

Страницы администрирования и консоли разделяют ОДИН контракт заголовка:
страница владеет кластером действий в правом верхнем углу через слоты с
объявленным назначением, и именно в этом кластере — а не в теле страницы —
живут её основные точки входа.

## Канонические слоты

Каждая регистрация объявляет НАЗНАЧЕНИЕ; кластер рендерит канонические слоты
по рангу, независимо от порядка регистрации представлений:

```text
[создать][фильтр][поиск][обновить][окно]
```

Регистрации с назначением вне канонических слотов — пользовательские: они
рендерятся ПОСЛЕ канонической зоны, утрамбованные справа налево в обратном
порядке регистрации — каноническая зона никогда не сдвигается.

## Правило создания

Основное действие создания страницы — то, что создаёт новую сущность верхнего
уровня (провайдера, канал, группу, правило доступа, тему на общей линии) —
это **кнопка с иконкой плюса в кластере справа вверху, слева от обновления**.
Это никогда не отдельная кнопка внутри тела страницы.

Видимая подпись, которую носила бы кнопка в теле, становится доступным именем
и подсказкой кнопки; диалог создания остаётся во владении самой страницы.

**Контекстные добавления освобождены.** Плюс, добавляющий строку в подсписок
внутри редактора, диалога, мастера или карточки («добавить строку модели»,
«добавить участника», «добавить схему монтирования») — часть локальной
грамматики, а не действие создания страницы; он остаётся на месте.

## Геометрия

Кластер — это один ряд хрома: каждая кнопка-иконка идёт по одной и той же
лестнице размеров (`useChromeActionSize`), глифы 16 px. Кнопка с жёстко
заданным размером между соседями лестничного размера читается как другое
семейство — собирайте кластер из общих хелперов, никаких прибитых вручную
размеров.

## Эталонная реализация

Хром поставляет hikari: ряд действий `HkAdminHeader`, `HkIconButton` и
`useChromeActionSize`. Хосты регистрируются через пару композаблов
`provideActionBar` / `useActionBar`, рендерящую слоты выше; она — эталонная
реализация этой грамматики.

## Мобильное свёртывание

Группа кнопок, закреплённая в центральном слоте шапки или подвала,
свёртывается на телефонных ширинах (<768, `useBreakpoint().isMobile` —
порог семейства sheet): полоса становится триггером-селектором,
называющим АКТИВНЫЙ пункт, а его опции открываются нижним листом
(`HkSelectPanel` с `sheetOnMobile`). Обе формы ведёт один контракт
значения — глубокие ссылки `?tab=` переживают точку перелома.
`HkAdaptiveTabs` — реализация по умолчанию; переключатели динамических
списков проектов с собственными строками (переключатель платформ) — освобождённое
исключение, а не образец для подражания.

## Листы выбора и закреплённый поиск

Раскрывающаяся поверхность (`HkSelectPanel` — под `HkSelect` / `HkMenu` /
чип-селекторами) имеет две полосы содержимого, и то, к какой полосе что
относится, не обсуждается:

- **`default` прокручивается.** Строки, карточки, каталоги — всё, что может
  перерасти поверхность.
- **`pinnedHeader` не прокручивается.** Хром, который должен оставаться
  доступным, пока список прокручивается: прежде всего поле живого фильтра.
  Оно рендерится вне зоны прокрутки в обеих формах — полосой под строкой
  заголовка листа на телефоне, головой колонки popout на десктопе (тогда
  единственную полосу прокрутки несёт тело). Поле поиска внутри
  прокручиваемого содержимого уезжает с первым жестом — это дефект, а не
  стилевой выбор (2026-11-27).

Телефонные листы семейства селектор/меню облегают содержимое до **80 %
вьюпорта**; более длинное содержимое прокручивается внутри. Потолок,
настроенный для десктопного popout (`maxHeight`, напр. `min(18rem, 45dvh)`),
никогда не доходит до листа. Лист также обрывает цепочку прокрутки: жест по
ручке, строке заголовка или закреплённой полосе никогда не тянет страницу
сзади.

## Движение списков

Всякий раз, когда элементы списка меняются — добавляются, удаляются,
перестраиваются — перемещение идёт через `HkListTransition` hikari
(ключевой `TransitionGroup`, чей FLIP сообщается шине анимации рантайма), а
не через самодельный твин. Один умолчание для всех поверхностей в форме
списка (строки, карточки, каскады): трек перемещения — 0,3 с, вход и выход —
по 0,15 с и начинаются одновременно с перемещением. Хост настраивает пропсами
`duration` / `enterDuration` / `leaveDuration` (CSS-времена; одинокий
`duration` выводит обе половины). `surface` — единственное исключение
(строки-окна сохраняют тайминги входа/выхода семейства окон).

Мульти-селектор (`HkAffixPicker` в режиме `multi`, `layout="rows"`) ничего
не строит перед поиском ради своей выборки: отмеченные строки несут галочку
слева и всплывают наверх в порядке каталога под разделителем; тап
переключает строку, и она скользит к своему месту или обратно.
`layout="tags"` — форма редактора значений (по каждому пункту показано
введённое значение) и сохраняет список тегов над поиском.

## Текст в углах футера

Текст в любом из шести углов хедера/футера (лево/центр/право ×2) идёт через
hikari-компонент `HkCornerText`: один экземпляр = одна текстовая дорожка одного
угла.

- `align` задаёт угол: `start` (левые углы) / `center` (центральная дорожка) /
  `end` (правые углы); перенесённые строки держатся того же края — дорожка
  правого угла остаётся выровненной вправо и после переноса.
- Элементы — атомы `nowrap`: дорожка переносит МЕЖДУ элементами и никогда
  внутри одного (номер регистрации не должен рваться посреди номера).
- По умолчанию приглушённый хром (`text-2xs` + 0.6 непрозрачности);
  `muted: false` возвращает полную насыщенность.
- Несколько строк в одном углу (строка имени над строкой регистраций) —
  стопка экземпляров вертикально; фиксированная 3rem-полоса статуса вмещает
  две строки text-2xs.
- Элемент `items` имеет вид `{ key, text, href? }`: `key` — стабильный
  идентификатор для рендерера списка, `text` — отображаемая строка (номер
  регистрации, имя системы, …), `href` необязателен — без него элемент
  рисуется как обычный `<span>`, с ним — как ссылка.
- Элемент с `href` всегда открывается в новой вкладке: `target="_blank"` и
  `rel="noopener noreferrer"` (тот же контракт, что у номера регистрации —
  сторонний сайт не должен получать дескриптор окна страницы входа). Это
  поведение самого компонента: хост не должен оборачивать элементы в свой
  `<a>`.
- Ссылочные элементы (регистрации) — через `items` + `as="nav"` +
  `ariaLabel`; произвольное содержимое (чип состояния) — через слот по
  умолчанию, после `items`.

Хостам запрещено вручную писать сжимающие дорожки с `flex-wrap: nowrap` и
выпускать текст за пределы полосы фиксированной высоты. Эталонная реализация:
`HkCornerText`.
