# 頁面骨架：動作區語法

管理與主控台頁面共用同一份頁頭契約：頁面透過「宣告用途的槽位」擁有右上角動作區，
頁面的主要入口住在動作區裡——而不是頁面正文裡。

## 規範槽位

每個註冊都宣告一個用途；動作區按槽位的固定次序渲染，與視圖註冊的先後無關：

```text
[新增][篩選][搜尋][重新整理][視窗]
```

用途不屬於規範槽位的註冊是自訂項：排在規範區之後、按註冊的逆序由右向左填充，
規範區永遠不被擠動。

## 新增規則

頁面的主建立動作——建立一個新的頂層實體（一個提供者、一個頻道、一個群組、一條
準入規則、共享主題線上的一套主題）——是**右上角動作區裡的加號圖示按鈕，位於重新整理
左邊**。它絕不是頁面正文裡的獨立按鈕。

原本印在正文按鈕上的可見文案，成為該按鈕的無障礙名稱與懸浮提示；建立用的對話框
仍由頁面自己擁有。

**局部新增不受此限。** 在編輯器、對話框、精靈或卡片內部的子清單裡加一列（「新增
模型列」「新增成員」「新增掛載方案」）屬於那層局部語法，不是頁面的建立動作，留在
原地。

## 幾何

動作區是一整排 chrome：每個圖示按鈕都走同一套尺寸階梯（`useChromeActionSize`），
圖示配 16px。一個寫死尺寸的按鈕混在階梯尺寸的鄰居中間，會被讀成另一族按鈕——
用共享的組合式函式組裝動作區，不要手釘尺寸。

## 參考實作

chrome 由 hikari 提供：`HkAdminHeader` 的動作列、`HkIconButton` 與
`useChromeActionSize`。宿主經渲染上述槽位的 `provideActionBar` /
`useActionBar` composable 對註冊；它是這套語法的參考實作。

## 行動端摺疊

錨定在頁首中槽或頁尾中槽的按鈕組，在手機寬度視口（<768，`useBreakpoint().isMobile`——
sheet 家族的閾值）摺疊為：原按鈕組變成一個讀出**當前項**的下拉式觸發鈕，選項
以底部 sheet 展開（`HkSelectPanel` 的 `sheetOnMobile`）。兩套形態共用同一份
value 契約，`?tab=` 深鏈跨斷點不受影響。`HkAdaptiveTabs` 是預設實作；
自帶專屬行的動態項目列表切換器（平台切換器）是豁免的特例，不是可照抄的模式。

## 選擇器 sheet 與釘住的搜尋框

下拉面（`HkSelectPanel`——`HkSelect` / `HkMenu` / 各類晶片選擇器底下那一層）
有兩條內容帶，什麼東西歸哪條帶沒有商量餘地：

- **`default` 捲動。** 行、卡片、目錄——一切可能超出面板高度的內容。
- **`pinnedHeader` 不捲動。** 清單捲動時也必須夠得著的 chrome：首當其衝是
  即時過濾的搜尋框。它在兩種形態下都渲染在捲動區之外——手機上是標題列
  下方的一條帶，桌面上是 popout 欄的頭部（此時由 body 承擔唯一的捲軸）。
  搜尋框放在捲動內容裡、一滑就跟著捲走，是缺陷而不是風格選擇（2026-11-27）。

選擇器/選單家族的手機 sheet 貼合內容高度，最多到**視口的 80%**；更長的內容在
內部捲動。為桌面 popout 調的上限（`maxHeight`，例如 `min(18rem, 45dvh)`）永遠
不會作用到 sheet 上。sheet 還會截斷捲動鏈：在手柄、標題列或釘住帶上滑動，
不會拖動後面的頁面。

## 清單動效

只要清單項發生變動——新增、移除、重排——位移一律走 hikari 的
`HkListTransition`（帶 key 的 `TransitionGroup`，FLIP 向執行期動畫匯流排報備），
不許手搓補間。所有清單形表面（行、卡片、瀑布流）共用一個預設：移動軌道 0.3s，
進入與離開各 0.15s，並且與移動同時開始。宿主用 `duration` / `enterDuration` /
`leaveDuration` 三個 prop 客製（CSS 時間；只給 `duration` 時兩半自動推導）。
`surface` 是唯一例外（本身是視窗的行保留視窗家族的進出場節奏）。

多選選擇器（`HkAffixPicker` 的 `multi` 模式、`layout="rows"`）不會為選中項在
搜尋框前面新建任何東西：勾選的行帶左側勾選標記，依目錄順序浮到清單前部、
以一條分隔線與其餘行隔開；點一下即切換，行會滑到或滑回自己的位置。
`layout="tags"` 是值編輯器形態（每條顯示各自填寫的值），保留搜尋框上方的標籤列。

## 頁尾角落文字

頁眉/頁尾的六個角落（左/中/右 ×2）顯示文字，一律用 hikari 的 `HkCornerText`：
一個實例 = 一個角落的一條文字道。

- `align` 決定對齊：`start`（左角）/`center`（中道）/`end`（右角）；條目換行後
  繼續貼著同一側——右角的文字折行仍靠右。
- 條目是 `nowrap` 原子：條目**之間**換行，條目內部永不折行（備案號不得斷在
  序號中間）。
- 預設 chrome 弱墨（`text-2xs` + 0.6 不透明度）；`muted: false` 恢復全墨。
- 一個角落要多行（識別行 + 備案行）就縱向堆疊多個實例——固定 3rem 狀態帶內
  容得下兩行 text-2xs。
- `items` 的條目形狀是 `{ key, text, href? }`：`key` 是列表渲染的穩定識別，
  `text` 是顯示文字（備案號、系統名……），`href` 可省略——省略時渲染成普通的
  `<span>`，給出則渲染成連結。
- 帶 `href` 的條目一律在新分頁開啟：`target="_blank"` + `rel="noopener noreferrer"`
  （與備案號同一契約——外站不得持有登入頁視窗的句柄）。這是元件的行為，宿主
  不要自己再包一層 `<a>`。
- 連結條目用 `items` + `as="nav"` + `ariaLabel`；自由內容（狀態
  晶片）走預設插槽，排在 `items` 之後。

宿主不得再手寫 `flex-wrap: nowrap` 的單行擠壓道，也不得讓文字溢出固定高度帶。
參考實作：`HkCornerText`。
